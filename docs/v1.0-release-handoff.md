# Director OS v1.0 release handoff

Director OS v1.0 is the first complete code-owned launch candidate. The repository contains the autonomous production loop, Director Camera, revisions, Director Memory, authenticated workspaces, billing and subscriptions, governance, observability, disaster recovery, real FFmpeg qualification, full-stack rehearsal, security audits, SBOM generation, and release packaging.

## Release decision

A deployment is a **GO** only when all of the following are true:

1. Backend CI passes.
2. Frontend CI passes.
3. Release Qualification passes the real FFmpeg render and complete Compose rehearsal.
4. Security and Supply Chain produces clean dependency audits and CycloneDX SBOMs.
5. Director OS v1 Release Candidate produces the versioned source bundle and manifest.
6. `ops/go_live.sh` passes against the real production environment and deployed HTTPS URL.
7. Human legal, media-rights, privacy, and operational approvals are recorded outside the repository.

The release doctor never converts missing infrastructure into a false success. External credentials and rehearsals remain `PENDING` until supplied and verified.

## One-command production gate

Run from the repository root after preparing the real production environment file:

```bash
bash ops/go_live.sh /secure/path/director-production.env https://director.example.com
```

The command:

- rejects unsafe authentication, schema, CORS, proxy, rate-limit, metrics, database, and readiness settings;
- verifies that SMTP, ACME, object storage, Stripe, transcription, and off-host backups are configured;
- checks remote TLS, liveness, dependency readiness, and protected metrics;
- validates the production Compose model;
- runs the authenticated deployment smoke checks when credentials are supplied;
- writes the release doctor report, source manifest, and SHA-256 checksums into `dist/`.

A non-zero exit code is a **NO-GO**.

## Required external rehearsals

These cannot be completed by repository code alone and must be executed with real accounts and infrastructure:

- DNS points to the intended host and Caddy obtains a trusted certificate.
- SMTP verification, invitation, and password-reset messages arrive at major mailbox providers.
- S3-compatible multipart upload, ETag exposure, download, lifecycle expiry, and permanent deletion work with production IAM.
- Stripe test mode covers checkout, webhook replay, paid renewal, payment failure, portal access, plan change, and cancellation before live keys are enabled.
- The configured transcription provider processes representative customer speech and failure modes are acceptable.
- Backups are encrypted and copied off-host; a destructive restore is completed in a disposable environment.
- Monitoring receives metrics and logs, and alert routes reach the on-call operator.
- Representative real customer media completes upload, Director Camera, render, revision, secure delivery, export, and deletion on the target host.
- Capacity tests use the expected launch concurrency, file sizes, and render durations.

## Deployment sequence

1. Back up the database, Redis state, and persistent Director data.
2. Store the v1.0 release manifest, SBOMs, audit reports, source archive, and checksums with the deployment record.
3. Pull the exact release tag or merge SHA.
4. Run `docker compose --env-file <production.env> -f compose.production.yml config`.
5. Run the release doctor locally without `--allow-external-pending`.
6. Build or pull the immutable application images.
7. Run the migration service and verify Alembic head.
8. Start PostgreSQL, Redis, API, worker, beat, frontend, and Caddy.
9. Run `ops/go_live.sh` with the deployed HTTPS URL.
10. Complete a real-media production and secure-download check.
11. Enable public traffic only after every gate is green.

## Rollback

Rollback is triggered by failed migrations, readiness failure, elevated 5xx responses, worker disconnects, broken signed delivery, incorrect billing behavior, or failed real-media production.

1. Stop new mutations and production submissions.
2. Keep the last publishable project outputs intact.
3. Restore the previous immutable application revision.
4. Restore database and persistent data only when the schema or data was changed incompatibly.
5. Run Alembic and the deployment smoke test against the restored revision.
6. Record the request IDs, release manifest SHA, failure evidence, and corrective action.

## Evidence retained by CI

- Backend test log
- Real media-render log
- Full-stack service log
- Backend and frontend audit JSON
- Backend and frontend CycloneDX SBOMs
- Release doctor JSON and Markdown
- Release manifest and source-file hashes
- Source archive and checksum file

Those artifacts identify exactly what was tested and deployed. They do not substitute for the external rehearsals above.
